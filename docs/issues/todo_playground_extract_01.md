# Playground を汎用の実行・創作環境として切り出す構想

作成日：2026-10-16
状態：検討メモ。切り出しの実装・公開 API・パッケージ名は未決定。

## 背景と目的

`tetorica-fm2612` の npm ページから Playground へ移動し、その場でコードを編集して音を試せる導線を用意した。
この体験を、他のライブラリや創作用途にも提供できる可能性がある。

目指す体験は「独自の API とサンプルを載せると、編集・実行・保存・共有までできる遊び場を用意できる」こと。
音楽、ゲーム、ロボット対戦、シミュレーションなどを用途の候補とする。
コードを書く過程や、結果をすぐ動かして遊ぶことにも価値を置く。

## 共通部分の候補

以下は切り出し候補であり、現時点でそのまま独立利用できると確認した一覧ではない。

- エディター、ファイル一覧、補完・型定義など、利用する API を触るための画面。
- Run／Stop、実行状態、ログ・エラー表示、実行終了時の後始末。
- Virtual Files によるコード・素材・設定の管理、Sync／Revert。
- Cassette によるプロジェクトの受け渡し。受け取った人が開いて続きを触れること。
- Shell と MCP による操作。必要な用途で組み込めるかを検討する。

`tetorica-virtual-files` は既存パッケージを再利用する。
音源、音声時計、拍・BPM、音楽用 UI は音楽側が担当する候補とし、実行管理との境界はコード調査で確認する。
Git 通信・資格情報・native 音声など、Tauri に依存する機能の提供方法も別途整理する。
すべての用途に全機能を必須にするかどうかは、実際の利用例から判断する。

## 進める場合の順序

1. 音楽用 Playground を使い続け、既存機能の品質を保つ。
2. 別の小さな用途を一つ選び、独自 API・サンプル・結果表示を載せる試作を行う。用途は未決定。
3. 二つの利用例で共通する処理と、用途ごとに必要な処理を確認する。
4. 確認できた範囲から小さく切り出し、組み込み例・型定義・ドキュメントを用意する。

初期段階では既存構成を活用し、必要な変更に範囲を絞る。
公開パッケージの分割数や拡張機構は、試作を通して決める。

## 試作で確認すること

- 音楽に依存せず、API の型・サンプル・結果表示を差し替えて使えるか。
- Run のやり直し、Stop、例外、非同期処理の終了で、以前の処理やリソースが残らないか。
- 音楽側の liveLoop 置き換えなど、既存の実行仕様を維持できるか。
- コード・素材・設定を Cassette で渡し、別の環境で開いて編集・実行できるか。
- 複数の Playground を使う場合に、ファイル・実行状態・後始末が干渉しないか。
- ブラウザだけで動く範囲と、native 機能が必要な範囲を説明できるか。

ローカルサーバー化は関連する検討だが、汎用 Playground の切り出しに必須と決めてはいない。
MCP が存在することと、画面なしで動く実行サーバーが存在することも区別する。
