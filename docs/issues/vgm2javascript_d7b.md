# VGM High Import：オペレーター設定の集約と可読性改善

## 目的

既存の High Import を拡張し、生成 JavaScript を短く、編集しやすくする。
音楽的な意味を推測して音名やフレーズへ変換する前に、意味が確定している
レジスター操作と繰り返しを整理する。

最優先事項は、レジスター値・書き込み順・待ち時間を保持すること。
変換できない部分は raw write と sleepSamples のまま残す。
Schedule / Write の既存出力は変更しない。

## 現状と分析対象

High は現在、隣接する周波数レジスターのペアを fm.setFrequency() に、
KEY 操作を fm.keyOn() / fm.keyOff() に変換する。
DAC data file が有効なら、DACデータは仮想ファイルへ分離して読み込む。
このDAC機能は維持する。

今回の分析対象 o1.txt は 5,333行、約117 KiB。

- コメント：1,649行
- 残っている raw write：1,648件
- うち TL（Total Level、0x40系）設定：1,247件、約76%
- 同じ3オペレーターへのTL設定ブロック：62回
- 同じ4オペレーターへのTL設定とKEY ONのブロック：51回

上記はこのファイルの分析値であり、一般的なVGMでの削減率を保証しない。
最初の改善対象は、特に出現数の多いTL設定とする。

## 第1段階：既存APIへの置換

現在の出力例：

```js
// CH0 OP1: TL=20
write(0x40, 0x14);
```

変換後：

```js
fm.setOperator(CH1, OP1, { tl: 20 });
```

説明コメントとraw writeを、意味の分かる1行へ置換する。
既存APIを調査し、同じレジスター値と順序を再現できる操作から対応する。

- DT/MULTI、TL、RS/AR、AM/D1R、D2R、SL/RR、SSG-EG：setOperator()
- ALG/FB：setAlgo()
- PAN/AMS/PMS：setPan()
- LFO：setLfo()
- DAC有効／無効：setDacEnabled()

レジスターが複数フィールドを持つ場合は、その書き込みに含まれる全フィールドを
指定する。API内部の既定値や、raw writeと同期しているとは限らない内部状態に
依存してはいけない。

予約ビットなど、APIで同じ値を再現できない書き込みはrawのまま残す。
0x27のタイマー・CSM・CH3特殊モード制御は、単純な特殊モードAPIへ置換しない。
物理スロット順と公開APIの論理オペレーター番号の対応を確認する。

## 第2段階：順序を保持する fm.setOperators() の追加

以下は新規APIの提案であり、現在は未実装。
TL専用APIではなく、既存のsetOperator()を配列順に適用する汎用APIとする。
setLevels()は別途追加せず、TLもこのAPIで扱う。

```js
fm.setOperators(CH1, [
  [OP1, { tl: 20 }],
  [OP3, { tl: 24 }],
  [OP2, { tl: 20 }],
]);
await sleepSamples(3);
fm.setOperator(CH1, OP4, { tl: 27 });
fm.keyOn(CH1);
```

### API仕様案

```ts
setOperators(
  channel: YM2612Channel,
  entries: Array<[YM2612Operator, YM2612OperatorParams]>
): void;
```

パラメーター型は既存のYM2612OperatorParamsを再利用する。
`multi`、`ssg`、`am: boolean`など、既存setOperator()と同じ名前・型・範囲を使う。
`multiple`や`ssgEg`という別名は導入しない。既存の`sr` / `d2r`の扱いも揃える。

- 指定された配列順に、各エントリーをsetOperator()へ適用する。
- TLは0..127。小さいほど音量が大きい。
- 指定していないオペレーターには書き込まない。
- 同一オペレーターが複数回現れても、書き込みを省略しない。
- 入力全体（チャンネル、配列・タプル、オペレーター、設定値）を検証してから書き込みを開始する。
  検証段階で内部状態も変更せず、後続エントリーの入力エラーで一部だけ適用されるのを避ける。
- 内部のオペレーター状態も既存のsetOperator()と同様に更新する。
- 配列の並べ替え、同値書き込みの削除、追加のwaitは行わない。

o1.txt には OP1 → OP3 → OP2 → OP4 の順が多い。
単なる `[20, 20, 24, 27]` のような論理番号順の配列ではなく、
オペレーター番号を明示して元の順序を保持する。

### エントリー順とフィールド順

配列の順序は書き込み順を指定するが、設定オブジェクトのプロパティ記述順は
書き込み順を指定しない。各エントリー内は既存setOperator()の実装順となる。

```js
// 元の順序がTL → DT/MULTIなら、エントリーを分けて保持する。
fm.setOperators(CH1, [
  [OP1, { tl: 20 }],
  [OP1, { dt: 0, multi: 6 }],
]);
```

これを `[OP1, { tl: 20, dt: 0, multi: 6 }]` にすると、既存APIでは
DT/MULTI → TLの順で出力されるため、変換器はまとめてはいけない。

初版は「元の1レジスター書き込み＝1エントリー」を基本とする。
複数フィールドの統合は、既存APIが展開するレジスター列と元の列が
値・順序・回数まで一致する場合だけ行う。
同じオペレーターでも、間に別オペレーターの操作があれば移動して統合しない。

```js
fm.setOperators(CH1, [
  [OP1, { dt: 0, multi: 6 }],
  [OP3, { dt: 0, multi: 0 }],
  [OP1, { tl: 20 }],
  [OP3, { tl: 24 }],
]);
```

### 集約条件

- 元のイベント列で連続している。
- 同じチャンネルの、setOperator()で正確に表現できる書き込みである。
- 同じサンプル時刻であり、途中にwaitがない。
- 他チャンネル、グローバル制御、KEY操作などをまたがない。
- DACを別ファイルに取り出した後に見かけ上隣接しても、元の並びを確認する。

単発設定はsetOperator()でよい。複数設定を集約した場合も、整形後の行数や文字数が
増えないよう、短い配列は1行で出力するなど出力形式を調整する。

## 第3段階：同一設定の定数化

```js
const operators001 = [[OP1, { tl: 20 }], [OP3, { tl: 24 }], [OP2, { tl: 20 }]];

fm.setOperators(CH1, operators001);
```

- オペレーター番号・指定フィールド・値・配列順が完全一致する設定を共有する。
  フィールドの省略と明示的な値指定を同一扱いしない。
- チャンネルに依存しない設定配列は、複数チャンネルから利用できる。
- 同じ値が設定済みでも、呼び出し自体を削除しない。
- 定義と参照を合わせて短くなる場合だけ定数化する。
- 同じ入力から同じ名前・順序を生成し、差分を比較しやすくする。
- ファイル名や音色から「bass」などの用途を推測して命名しない。

## 第4段階：頻出操作列の関数化

```js
function trigger001(channel) {
  fm.setOperators(channel, operators001);
  fm.keyOn(channel);
}
```

同じ順序・引数構造の操作列が何度も現れる場合、関数へ抽出する。
初版はwaitを含まない同一時刻の操作列に限定する。
チャンネルを引数化する場合は、対象操作が同じチャンネルへ一貫して対応することを確認する。

過剰な関数化は読みづらいため、出現回数と操作数、定義込みの削減量で判定する。
閾値は実測で決定する。すべての操作を小さな関数へ分割する方式にはしない。

## 今回まとめないもの

### 待ち時間をまたぐ音色全体のsetPreset()化

o1.txt では音色設定の途中に sleepSamples(2) / sleepSamples(3) が入る。
setPreset()の一括適用では、その時間差や書き込み順を保持できない場合がある。
発音していないように見えても、リリース中の音や他チャンネルへの影響を
無視して安全と判定しない。

### 同値書き込みの削除

設定値が同じという理由だけで削除しない。
レジスターの副作用まで検証した別の最適化として扱う。

### 音名やplay()への変換

BLOCK/FNUMの丸め、KEYマスク、音の途中の設定変更などを扱う別段階とする。
durationSamplesなどのAPI追加も今回の必須範囲には含めない。

### write()からfm.write()への表記変更

今回の圧縮・可読性改善とは分けて扱う。

## 実装構成

VGMの解析済みイベントから直接変換する。
生成JavaScriptを再び文字列解析して最適化する方式にはしない。

1. 元イベントにサンプル時刻・通し番号・port・register・valueを保持
2. 既存APIに正確に対応する操作へ変換
3. 元の隣接関係と時刻を使ってオペレーター設定をsetOperators()へ集約
4. 同一設定配列を抽出
5. 頻出操作列を抽出
6. JavaScriptを生成

主な対象：

- web/ym2612vgm.js：High変換
- web/ym2612synth.js：setOperators()追加、既存setOperator()と検証処理を共有
- docs/playground/tetorica-playground-globals.d.ts：API型定義
- docs/playground/index.html：人向けHelperの説明
- docs/playground/vgm_export.test.mjs：生成結果と実行結果の検証
- webとdocs/jsの対応ファイルの同期、および配布経路の確認

他チップの共通FM APIにも追加する場合は、対応チャンネルと実装を確認してから行う。
Highの対象範囲を暗黙に拡張しない。

## 検証

生成コードを実際のFM APIと記録用transportで実行し、
`[timeSamples, port, register, value]` の列を変換前と比較する。
文字列の短縮だけで成功と判定しない。

- 全6チャンネル、port 0 / port 1
- 論理オペレーターと物理スロットの対応
- 各フィールドの境界値、予約ビットを含むrawフォールバック
- 配列順、同一オペレーターへの反復書き込み
- TL以外も含む混合設定列、同一オペレーターの分割エントリー
- オブジェクトのプロパティ順に依存せず、既存APIの書き込み順を使うこと
- 複数フィールド統合で順序が変わる場合はエントリーを分けること
- 共有レジスターの全フィールド指定により、古い内部状態に依存しないこと
- 後続エントリーが不正な場合、書き込みと内部状態更新が一切発生しないこと
- 1 / 2 / 3サンプルのwaitをまたいで集約しないこと
- 他チャンネル・グローバル操作が間に入るケース
- 部分KEYマスク、CH3特殊モード、タイマー操作の保持
- 定数化・関数化の前後で書き込み列が一致すること
- DACデータ分離、Include DAC、Worker実行との併用
- 既存Schedule / Writeの回帰テスト

DAC分離が有効な場合は、DACバンクの時刻・値とFM側のイベントを個別に検証する。
このテストはイベント列の保持を検証するもので、ブラウザ実時間での
再生タイミングや音声波形の完全一致を保証するものではない。

o1.txtの元VGMが利用できる場合は、同じ入力の変換前後で行数・文字数・raw write数・
集約数を測定し、音声再生も確認する。o1.txtだけから元VGMを推測復元しない。

## 実装順序

1. 既存APIへの単独書き込みの置換と厳密な回帰検証
2. setOperators()追加と同時刻・同一チャンネルの連続設定の集約（TLを優先）
3. 設定配列の定数化
4. 頻出操作列の関数化

まず1〜2で実際の削減量と読みやすさを確認し、3〜4を段階的に進める。
