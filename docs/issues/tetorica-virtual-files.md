# Tetorica Virtual Files

状態：構想・実装計画の整理。パッケージ名と API は仮案。

## 目的

Playground の仮想ファイルシステムを汎用ライブラリーとして独立させる。
その上に軽量シェル、Git、小さな JavaScript 用ツールを載せ、同じファイルを操作できる環境を作る。

想定する流れは次のとおり。

```text
virtual_files
  ├─ Playground の FILES / エディター
  ├─ 軽量シェル
  │    ├─ ファイル操作・検索
  │    ├─ JavaScript の整形・構文チェック
  │    └─ Git
  └─ 保存・復元アダプター
       ├─ IndexedDB
       └─ 実フォルダー（将来）
```

ツールは OS のファイルを直接操作せず、環境から渡されたファイルシステムを使う。
まず Playground を利用者として育て、別のエディターや制作ツールからも使える形を目指す。

## 現状

- `docs/playground/playground_virtual_files.js` が、メモリー上の `Map` にパス・テキスト・バイナリを保持する。
- 読み書き、一覧、削除、全体の置き換え、変更通知、相対パス解決、ファイル／フォルダーのコピー・移動がある。
- ディレクトリーは主にファイルのパスから推定している。空のディレクトリーとルートを扱う API は追加が必要。
- 同じモジュールに、Playground の動的 import の書き換えや、実行用の JavaScript コード生成も含まれている。
- Tauri 版は `playground_autosave.js` を通して IndexedDB にプロジェクトを保存し、起動時にメモリーへ復元する。
- Cassette の ZIP 入出力は別モジュールで行う。現在の仮想ファイルは OS の実ファイルに対応していない。
- New Cassette は初回起動と同じコード・フォルダー・README・付属サンプルを復元する。

現在の `/index.js` の移動禁止や `/sys` の扱いは Playground の都合であり、汎用ライブラリーの固定ルールにはしない。

## 配置と配布

実装も含めて `packages/virtual-files/` に置く。
既存パッケージのように配布情報だけを分ける構成ではなく、独立したライブラリーとして整理する。

```text
packages/virtual-files/
  package.json
  README.md
  src/
    filesystem.js
    path.js
    shell.js
    commands/
    adapters/
      indexeddb.js
  tests/
```

npm 名は `tetorica-virtual-files` を候補とする。
Git と JavaScript 用ツールはコアへの必須依存にせず、登録できる拡張にする。
保存アダプターも個別に import できるようにし、Node.js でコアを使うだけならブラウザー API を必要としない構成にする。

Playground はこのライブラリーを直接利用する。
`tetorica-fm2612` から利用することも可能で、必要になった段階で依存・再公開を検討する。

```javascript
// 独立パッケージとしての利用案
import {createVirtualFileSystem} from 'tetorica-virtual-files';

// FM パッケージから再公開する場合の利用案
import {createVirtualFileSystem} from 'tetorica-fm2612/virtual-files.js';
```

後者の export は追加する場合の案であり、現在の公開 API ではない。
音源を利用するだけの人にシェルや Git の依存を持たせない。
ブラウザー用の配布 ZIP にも同じ実装を含めるビルド手順を用意する。

## ファイルシステム

最初に次の役割をコアとして分離する。

- テキスト／バイナリの読み書きとファイル情報の取得。
- ルート、実ディレクトリー、空ディレクトリー、階層一覧。
- パスの正規化と解決。ファイルからの相対 import と、シェルの作業ディレクトリーからの解決を区別する。
- 作成・コピー・移動・削除。衝突や不正な移動を、変更前に検証する。
- スナップショットの取得・復元と変更通知。
- 複数ファイルをまとめて変更する仕組み。途中の状態を自動保存しないようにする。

作業ディレクトリーはシェル側が保持する。ファイルシステム自体に一つのグローバルな `cwd` を持たせない。
読み取り専用の組み込みファイルなどは、利用側が指定するポリシーとして扱う。
読み出したバイナリを変更しただけで内部データが変わることのないよう、コピーと変更通知の契約を明確にする。

JSDoc と `.d.ts` を提供し、利用者が補完・定義ジャンプで API を発見できるようにする。

## 軽量シェル

シェルはコマンドを JavaScript の関数として登録し、引数、入力、出力、終了コード、中断用の signal を扱う。
ユーザーが入力したコマンド文字列をそのまま `eval` する構成にはしない。

初期コマンド候補：`pwd`、`ls`、`cd`、`cat`、`mkdir`、`cp`、`mv`、`rm`。
まず引用符を含む引数解析と一つのコマンドの実行を作り、パイプやリダイレクトは後の段階で検討する。
完全な POSIX シェルを再現することは初期目標にしない。

```javascript
// API の形を説明するための仮案
const fs = createVirtualFileSystem();
const shell = createShell({fs});

shell.register('format', createJavaScriptFormatCommand({fs}));
shell.register('git', createGitCommand({fs, http}));

await shell.execute('ls /lib');
```

Playground の FILES とシェルは同じファイルシステムを共有する。
シェルからの変更をエディターへ反映し、エディターの未反映の変更もシェルから読めるようにする。
編集中のファイルの更新・削除・移動について、内容や表示の整合性を保つ。

## Git とツール

Git はコマンド登録とファイルシステムのアダプターで接続する。
JavaScript 製 Git の候補として isomorphic-git を検討し、採用前に必要な操作と互換性を確認する。

まずネットワークを使わない `init`、`status`、`add`、`commit`、`log` を対象にする。
Git 側が要求する `readFile`、`writeFile`、`readdir`、`stat`／`lstat`、`mkdir`、`unlink`、`rmdir` などの契約を確認し、現在の API に変換する。
ロックファイル、並行更新、バイナリ、シンボリックリンクなどの対応範囲も決める。

その後にリモートの fetch／push を追加する。
HTTP 通信は注入する別の機能とし、ブラウザーの CORS と Tauri 側の通信経路、認証方法を整理する。
認証情報を Cassette のファイルや通常のプロジェクトスナップショットに混ぜない。

`.git` の履歴も永続化する必要がある。
一方で Cassette の書き出しに履歴を含めるかは別の判断で、初期案では通常の Cassette ZIP から `.git` を除外する。

軽めのツールは、ファイル検索・テキスト検索・JavaScript の整形・構文チェックから始める。
それぞれが同じファイル操作 API とシェルの入出力を使う。

## 「閉じた環境」の範囲

ファイル操作を仮想ファイルシステムに限定することと、任意の JavaScript を隔離することは別の課題。
コマンドやツールには必要なファイル操作・通信機能を渡す形にするが、それだけで実行コードから OS やネットワークへのアクセスを禁止できるわけではない。

初期段階は、環境が登録したコマンドで JavaScript ファイルを編集・検索・検査できる範囲を対象にする。
任意の JavaScript の実行を追加する場合は、別途実行環境の隔離を設計する。Worker 化だけを安全な隔離と見なさない。

## 実装の順番

1. 現在の汎用ファイル操作を `packages/virtual-files/` に切り出す。Playground 固有のコード生成・実行処理は利用側に残す。
2. ディレクトリー、スナップショット、変更通知の契約を整理し、IndexedDB 保存を接続する。
3. Playground の FILES、Monaco、Cassette、自動保存を同じコアへ移行する。
4. 小さなシェルと基本コマンドを作り、FILES と同じ内容を操作できることを確認する。
5. JavaScript 用の検索・整形・構文チェックを拡張として追加する。
6. Git のファイルシステムアダプターを作り、ローカルの履歴操作を実装する。
7. 必要に応じて実フォルダー、認証、リモートとの通信、Git の UI を追加する。

最初の到達点は、Playground の既存機能を維持しながら、シェルの `ls` と `cat` で同じファイルを参照できること。
npm 公開や `tetorica-fm2612` からの再公開は、API と配布方法を確認してから進める。

## 確認すること

- Node.js とブラウザーでコアを利用でき、不要なブラウザー／音源依存を読み込まない。
- 相対パス、ルート、空ディレクトリー、移動の衝突、バイナリの内容を正しく扱う。
- エディターとシェルの変更が相互に見え、未反映の編集を上書きしない。
- 複数ファイルの変更を一貫した状態で保存し、再起動後に復元できる。
- New Cassette の初期ファイル一式と、既存の Cassette 入出力を維持する。
- Git の履歴を保存・復元でき、通常の Cassette 書き出しとは区別できる。

## 未決事項

- 独立パッケージの公開名と、シェル／Git 拡張を別パッケージにする範囲。
- シェルの構文、入出力 API、キャンセル、変更の競合処理。
- Git が必要とするファイル情報と、対応しない機能の扱い。
- 自動保存と `.git` の保存単位、サイズ、複数プロジェクトの切り替え。
- 実フォルダーを開く機能と Git 操作の UI。アプリ内でどこまで操作するかは利用して判断する。
