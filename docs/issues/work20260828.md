Please extend the Tetorica FM2612 Playground API with a small set of missing low-level YM2612 helpers and a simple sequencing helper for live coding.

Goal

Make the Playground easier to use for:

* YM2612 experiments
* educational examples
* low-level FM programming
* simple musical sequencing / live coding

Keep the existing API backward compatible.

Do not introduce unrelated refactoring.

Before implementing anything, inspect the current implementation and reuse existing helpers for:

* channel mapping
* logical operator mapping
* note parsing
* BLOCK/F-NUM calculation
* KEY ON/OFF
* choose()
* liveLoop()
* Playground live state

where possible.

⸻

1. Add explicit frequency control

Add:

fm.setFrequency(channel, block, fnum)

This should update the normal YM2612 channel frequency registers without triggering KEY ON.

Channel numbering must remain the public logical numbering:

0..5

This API is important because currently:

fm.noteOn(channel, block, fnum);

combines frequency setup and KEY ON.

We want examples to be able to show the YM2612 sequence explicitly:

fm.setFrequency(CH1, 4, 553);
fm.keyOn(CH1);

Do not remove or change the existing noteOn() behavior.

⸻

2. Add explicit KEY ON / KEY OFF helpers

Add:

fm.keyOn(channel, operators?)
fm.keyOff(channel, operators?)

Suggested TypeScript declarations:

keyOn(channel: YM2612Channel, operators?: YM2612Operator[]): void;
keyOff(channel: YM2612Channel, operators?: YM2612Operator[]): void;

Public logical operator numbering is:

OP1 = 0
OP2 = 1
OP3 = 2
OP4 = 3

These are logical operator numbers and may not match the YM2612 physical slot bit order directly.

Internally convert logical operator numbers to the correct YM2612 register 0x28 operator bits.

If operators is omitted, operate on all four operators.

Examples:

fm.keyOn(CH1);
fm.keyOff(CH1);
fm.keyOn(CH1, [OP1, OP2]);
fm.keyOff(CH1, [OP1, OP2]);

Preserve the existing:

fm.noteOn(...)
fm.noteOff(...)

APIs.

Prefer implementing the existing APIs using the new lower-level helpers if that keeps their current behavior exactly the same.

⸻

3. Add note-name to BLOCK/F-NUM conversion

Add a Playground helper:

noteToBlockFnum(note: string): {
  block: number;
  fnum: number;
};

Expose it both globally and through pg:

noteToBlockFnum("C4");
pg.noteToBlockFnum("C4");

Use the same note parsing and tuning assumptions already used by play().

Do not introduce a second independent pitch conversion implementation if an existing internal helper can be reused.

Example:

const { block, fnum } = noteToBlockFnum("C4");
fm.setFrequency(CH1, block, fnum);
fm.keyOn(CH1);
await sleep(0.5);
fm.keyOff(CH1);

The purpose is educational.

Users should be able to see the path:

note name
  -> BLOCK / F-NUM
  -> frequency registers
  -> KEY ON

6. Add cycle() sequence helper

Add a cycle() helper that complements the existing choose() helper.

choose(values) randomly selects an item.

cycle(values) returns items sequentially and wraps back to the beginning.

The intended usage is deliberately simple:

liveLoop("lead", async () => {
  const notes = scale("E4", "minorPentatonic", 2);
  await play(cycle(notes), {
    channel: CH2,
    duration: 0.08,
  });
  await beat(0.125);
});

The conceptual behavior is:

cycle(["C4", "E4", "G4"]); // C4
cycle(["C4", "E4", "G4"]); // E4
cycle(["C4", "E4", "G4"]); // G4
cycle(["C4", "E4", "G4"]); // C4

The important API symmetry is:

choose(notes); // random selection
cycle(notes);  // sequential selection

Do NOT require users to create an iterator:

// Do not require this style:
const notes = cycle([...]);
notes.next();

The desired style is simply:

play(cycle(notes));

Public declaration:

/** Return the next item in a repeating sequence. */
declare function cycle<T>(values: T[]): T;

Expose it through pg too:

declare const pg: {
  // ...
  choose: typeof choose;
  cycle: typeof cycle;
  // ...
};

So both forms work:

cycle(notes);
pg.cycle(notes);

7. cycle() state behavior

cycle() must preserve its position across repeated executions of a liveLoop.

Be careful with code like:

liveLoop("lead", async () => {
  const notes = scale("E4", "minorPentatonic", 2);
  await play(cycle(notes), {
    channel: CH2,
    duration: 0.08,
  });
  await beat(0.125);
});

scale() may return a new JavaScript array on every loop iteration.

Therefore, do not rely solely on array object identity, such as:

WeakMap<Array, number>

if doing so causes the sequence to restart on every iteration.

The example above must naturally produce:

E4
G4
A4
B4
...

rather than repeatedly returning the first note.

Also make independent cycle() call sites advance independently.

For example:

const notes = scale("E4", "minorPentatonic", 2);
const durations = [0.125, 0.125, 0.25, 0.5];
liveLoop("lead", async () => {
  await play(cycle(notes), {
    channel: CH2,
    duration: 0.08,
  });
  await beat(cycle(durations));
});

The note sequence and duration sequence must have independent cursors.

Inspect the existing liveLoop() execution/state model before deciding how to identify a cycle call site.

Prefer a small solution consistent with the existing Playground architecture.

Do not introduce a large general-purpose sequencing framework just for this.

Handle an empty array safely and consistently with the existing behavior of choose() where appropriate.

9. Keep the implementation small

The Playground should still expose the YM2612 rather than abstracting it away.

Do not add MIDI-style abstractions, polyphony managers, sequencer classes, or other large abstractions as part of this task.

The intended API should remain readable:

// Musical convenience
const notes = scale("E4", "minorPentatonic", 2);
play(choose(notes));
play(cycle(notes));
// YM2612-level experiment
const { block, fnum } = noteToBlockFnum("C4");
fm.setFrequency(CH1, block, fnum);
fm.keyOn(CH1);
fm.keyOff(CH1);
