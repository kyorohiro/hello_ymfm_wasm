# Playground：高速レジスタ制御による音響表現

## 目的

Tetorica Playgroundで、SoundChipのレジスタを高精度な時間軸で制御できるようにする。

従来の `play()`、`beat()`、`liveLoop()` に加え、レジスタ値の高速な変化そのものを音楽表現として扱えるようにしたい。

最初の対象はAY-3-8910／YM2149とする。

Atari STで使われていた高速音量制御、PCM風のサンプル再生、周期的な音色変調などを、Tetorica上で再現・拡張できることを目指す。

将来的にはYM2612、YM2608、Sega PSGなどにも展開する。

## 基本方針

- 既存のBrowser／WASM／Nativeの構成を尊重する。
- 現在の演奏時計、予約書き込み、所有者管理、取消し機構を再利用する。
- 既存APIを壊さない。
- 音源ごとのレジスタ仕様を無理に共通化しない。
- 時刻指定、命令配送、取消しの仕組みを共通化する。
- JavaScriptのループで数千回／秒のレジスタ書き込みを行わない。
- 音声処理側で事前に予約された命令を実行する。
- Nativeのaudio callbackに新しいallocation、待機lock、同期IPCを持ち込まない。
- パフォーマンスの改善は実測に基づいて行う。

## 1. 既存実装の調査

まず、現在のコードから以下を確認する。

- `scheduleRegisters()` の実装と対応音源
- Browser／WASMでのレジスタ書き込みの時間精度
- Native側の予約キューと適用タイミング
- `beat()`、`sleep()`、`play()` との時計の関係
- Main／Worker間の非同期処理
- `stopLoop()`、Stop、再Run、dispose時の取消し
- レジスタ書き込みの所有者管理
- 大量の予約命令によるメモリー・CPU負荷
- 音源コアの内部クロックと出力サンプルレートの関係

既に利用できる機能があれば、新しいAPIを作らず再利用する。

調査結果から、現状のままで実現できること、拡張が必要なこと、実現が難しいことを区別する。

## 2. 最初に実現したいユーザーシナリオ

### Scenario A：高速音量制御

AY／YM2149の音量レジスタを、正確な時間間隔で更新する。

例えば、8kHz程度の更新周期で音量を変化させる。

JavaScriptから更新データをまとめて渡し、音声生成側で再生する。

### Scenario B：PCM風サンプル再生

音量レジスタの更新列から、短いPCMサンプルを再生する。

- 4bit音量値への変換
- 音量特性の考慮
- 更新周期の指定
- 再生・停止・繰り返し
- 他チャンネルとの同時演奏

実機の音量特性を使う場合と、線形に近い変換を使う場合の違いも確認する。

### Scenario C：周期的な音色変調

音量レジスタの更新周期を変化させ、通常のPSG演奏から高速変調による音響表現へ連続的に移行する。

更新周期、波形、変調深度を変更できるようにする。

### Scenario D：通常のLive Codingとの共存

`liveLoop()` で通常の音符を演奏しながら、別チャンネルで高速レジスタ制御を実行する。

`stopLoop()` は対象の所有者に属する予約のみを取り消し、無関係な演奏を止めない。

## 3. API設計

既存APIを調査したうえで、最小限の追加を検討する。

以下は概念例であり、実装仕様として確定したものではない。

```js
const psg = await useSoundChip("ay8910");

await psg.scheduleRegisters([
  { sample: 0, register: 8, value: 0 },
  { sample: 6, register: 8, value: 12 },
  { sample: 12, register: 8, value: 4 },
]);
```

特に次を明確にする。

- `sample` がどのサンプルレート・時間原点を基準とするか
- 相対時刻と絶対時刻の区別
- BPM変更時の動作
- 同一時刻の書き込み順序
- 予約受付完了と音源への適用完了の区別
- キュー上限と大量データの転送方法
- 遅延、取消し、失敗時の動作
- 手動KeyboardやPreset編集との競合
- Native／WASMで保証できる時間精度

サンプル単位より細かい精度が必要な場合は、チップ内部クロックとの関係を調査する。

## 4. 性能・安全性

8kHz以上のレジスタ更新を想定し、次を検証する。

- 大量のJS→Native IPCを発生させない
- 音声callbackの締切を守る
- 長時間演奏でキューが無制限に増えない
- Stopやdisposeで予約を回収できる
- 古いsessionやinstanceの命令が新しい音源へ届かない
- バッファ分割によってPCM出力が変化しない
- 予約データの転送・再生中に不要なコピーを増やさない
- 他のSoundChipの発音やMixer処理に影響しない

無音時の負荷、単独再生時の負荷、複数SoundChipとの混在負荷を測定する。

## 5. 検証

Browser／WASM／Nativeで同じ制御データを実行する。

- PCM出力の比較
- 44.1kHz／48kHz／96kHzでの検証
- 更新周期の正確性
- callbackサイズ変更時の一致
- Stop／再Run／dispose
- Main／Worker
- 長時間再生
- Mixer・FX・録音との共存

音声ファイルを生成し、実際に聴けるExampleも用意する。

測定値と聴感評価を区別し、WASMとの一致だけを実機再現性の証明としない。

## 6. 実装の進め方

1. 既存コードと公開APIを調査する。
2. 実現方法を比較し、最小の変更案を決める。
3. AY／YM2149で高速音量制御を実証する。
4. PCM風サンプル再生のExampleを作る。
5. 通常の `liveLoop()` との混在を確認する。
6. Browser／Nativeの出力と性能を比較する。
7. 必要な共通部分だけを整理する。
8. 他のSoundChipへの展開可能性を報告する。

## 重要な制約

今回の目的は、大規模な音響エンジンの再設計ではない。

レイヤーの責務変更、Package分離、公開APIの破壊的変更は、必要性を示してから別途判断する。

実装できるという理由だけで変更範囲を広げない。

また、既存の `scheduleRegisters()` で十分に実現できる場合は、新しい抽象化を作らない。

まず既存の仕組みで最小のExampleを成立させ、そこで確認された不足だけを補う。

**最終目標は、SoundChipのレジスタ変化そのものを、Live Codingで利用できる音楽表現にすること。**
