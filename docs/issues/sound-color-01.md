# 音から FM 音色を探すアプリの構想

## 目的と位置付け

単音 WAV を入力し、近く聞こえる FM 音色設定の候補を生成する。
元のパラメーターを一意に復元することより、手動で調整するより早く
使いたい音に近づけることを目標にする。異なる設定が似た音になる場合もある。

自作部分を BSD-3-Clause で公開する方向で検討する。
手元で動作し、候補を比較・編集でき、TFI / JSON で持ち帰れる道具を目指す。
採用するライブラリ、モデル、プリセット、評価用音声の利用条件は個別に確認する。

まず別アプリで検証する案。VGM Analyzer への統合は急がない。
現在の ymfm、音色設定 API、TFI / JSON 出力の再利用範囲を調べる。
PCM の採譜・MIDI 化とは別の課題だが、Sample Explorer で取り出した
サンプルを入力に使える。以下は設計案で、音色推定機能は未実装。

## 最初の対象

- YM2612 に限定する。
- 単音、一定音程、リバーブやディレイのない音から始める。
- 音程と、必要ならキーオン長・キーオフ位置を手動指定する。
- 最初は既知の FM 設定から生成した WAV で検証する。
- 和音、演奏フレーズ、音源分離、自動採譜、CH3 special は初期対象に含めない。

入力が C4 の1音だけなら、元音色の他の音域での振る舞いは確定できない。
FM は音域によって聞こえ方が変わるため、候補を複数音域で試聴できるようにする。
複数音程の入力がある場合は、それらをまとめて評価することを後段で検討する。

## 基本の流れ

1. WAV を読み込み、音程・発音範囲・キーオフ位置を指定する。
2. プリセットや制限したパラメーター範囲から候補を用意する。
3. 入力と同じ音程・キーオン長で候補を合成する。
4. 特徴量で近い候補を絞る。
5. 上位候補の周辺パラメーターを変更し、再合成・比較する。
6. 複数候補を入力音と聴き比べ、手動調整または再探索する。
7. 選んだ音色を TFI / JSON で保存し、Playground などへ渡す。

初期版は学習モデルなしの検索・最適化で検証可能。
将来の推定モデルも「候補生成」の一手段として追加できる構成にする。

## 候補集と探索

FM のパラメーターは有限だが、全組み合わせの列挙は現実的ではない。
例えば20項目を各8段階に量子化しても、8^20 ≒ 1.15 × 10^18 通りになる。

- 許諾の明確な既存プリセット、制限したアルゴリズム・倍率・変調量から開始する。
- 最初は変更するパラメーターを絞り、残りを固定する。
- 粗い候補検索の後、TL・倍率・エンベロープ等の周辺を探索する。
- どの探索法を採るかは、計算時間と試聴結果を比較して決める。
- 候補の描画時間、候補数、特徴量の容量を測り、保存範囲を決める。
- 量子化で飛ばした設定に良い解がある可能性を考慮し、細かく再探索できるようにする。

候補集には、例えば C2 / C3 / C4 / C5 の音を持つ案がある。
ただし、入力音の評価には同じ音程での合成を使う。
別音域の候補音は、主に試聴や複数音程入力の評価に利用する。

## WAV から取るデータ（試作時の初期値）

以下の値は確定仕様ではなく、実データで調整する出発点。

### 前処理

- モノラル、44.1 kHz に揃える。
- 発音開始位置を揃える。短いアタックを切り落とさない。
- 音声全体に1つのゲインを適用して音量を正規化する。
- フレーム単位で正規化しない。音量の減衰が消えるため。
- 無音入力や極端に短い入力は明示的に扱う。
- キーオフ位置が不明なら、リリースの評価には不確実性があることを示す。

### 特徴量

| データ | 計算案 | 用途 |
| --- | --- | --- |
| RMS 音量 | 約20 ms窓、約10 ms間隔。dB に変換 | 立ち上がり・減衰・持続・リリース |
| 短い窓のスペクトル | 1,024サンプル、Hann 窓、441サンプル間隔で FFT | アタック付近の時間変化 |
| 長い窓のスペクトル | 4,096サンプル、Hann 窓、441サンプル間隔で FFT | 持続音・低音・細かな周波数成分 |
| 倍音分布 | 基音の整数倍近傍のパワーを集計。例：第1〜32倍音 | 倍音の形、候補との差の説明 |
| 明るさの推移（追加候補） | スペクトル重心を時系列化 | 鋭いアタックから丸い持続音への変化など |

FFT は WAV 全体に1回ではなく、短く区切って繰り返す（STFT）。
得るのは「周波数の一覧」だけでなく、各周波数成分の強さの時間変化。

A4=440 Hz なら、倍音分布は440、880、1,320 Hz…の周辺を集計する。
FFT のビンに正確に一致するとは限らないため、1ビンだけでは判断しない。
近傍幅は窓の分解能に合わせて決め、隣接倍音との重複と Nyquist 上限を扱う。
低音で倍音が分離できなければ、長い窓を追加するなどの調整が必要。

FM の金属音には整数倍から外れた成分もある。倍音表だけで判定せず、
スペクトル全体を保持する。基音相対の分布と、実周波数上の分布の両方を見る。

### データ構造の案

```javascript
{
  note: "A4",
  sampleRate: 44100,
  hopSamples: 441,
  rmsDb: [...],          // 時間
  spectrum1024: [...],   // 時間 × 周波数
  spectrum4096: [...],   // 時間 × 周波数
  harmonics: [...]       // 時間 × 倍音番号
}
```

実装時は窓・正規化方法・ゲイン・発音位置・キーオフ位置・特徴量の版も記録する。
大量の行列は JSON 配列に限らず、型付き配列やバイナリー保存を検討する。

## 類似度の初期案

- 音量差：対応する時刻の RMS[dB] の絶対差を平均する。
- スペクトル差：対応する時刻・周波数の log 振幅の絶対差を平均する。
- 短い窓と長い窓のスコアを別に持つ。
- 微小値の差に支配されないよう、例えば最大値から −80 dB を下限とする。
  入力と候補に同じ基準・計算規則を適用する。
- 配列サイズが違っても片方だけが支配しないよう、各項を正規化してから重み付けする。
- 長い無音や持続区間だけで評価が決まらないよう、比較区間と区間別の重みを持つ。

最初は RMS と2種類のスペクトルで順位付けし、倍音表は違いを説明する用途に使う。
軽い特徴量による候補検索と、上位候補の詳細評価は分けられるようにする。
総合点は知覚的な正解ではない。人の試聴順位と照合して改善する。

## UI の案

- 入力音と候補の交互試聴。
- 上位数件の候補と音色パラメーターを表示。
- 総合点だけでなく、アタック・持続・減衰の近さを表示。
- 波形、音量推移、スペクトログラム、倍音分布の比較。
- 音程・比較範囲・各評価項目の重みを調整。
- 鍵盤で別の音域も確認。
- 選んだ候補から再探索。探索中止と途中候補の試聴。
- TFI / JSON 保存。

例：ベルならアタックと減衰、オルガンなら持続部分を重視する。
既存 Playground の音色編集・試聴との受け渡しを優先し、統合時期は未定。

## 検証と実装順序

- [ ] 独立アプリの配置と、既存コードの再利用範囲を決める。
- [ ] 同じ設定・音程・キーオン長で再現可能な WAV 生成を用意する。
- [ ] WAV の前処理、RMS、2種類の STFT を実装する。
- [ ] 小さな候補集で検索・順位付け・試聴を通す。
- [ ] 既知の設定を含む候補集で、元音に近い音を検索できるか確認する。
- [ ] 元設定を含まない候補集で、近似と周辺探索の効果を確認する。
- [ ] パラメーター一致率に加え、再合成音の差・試聴評価・計算時間を記録する。
- [ ] 複数音域で評価し、1音だけに過剰適合していないか確認する。
- [ ] ベル、ベース、パッド、金属音など、異なる特性のテスト音を増やす。
- [ ] TFI / JSON の保存と、Playground 側での再生を検証する。
- [ ] 生楽器や PCM サンプルへ対象を広げる。
- [ ] 必要になった段階で学習モデル・GPU 利用を比較する。

WAV 読み込み、特徴量計算、距離計算、候補生成、合成、UI を分け、
DOM なしで音声とパラメーターを入出力するテストを可能にする。
同一音・ゲイン違い・開始位置違い・音程違い・無音を基本テストに含める。
ランダム探索には seed と評価条件を残す。
