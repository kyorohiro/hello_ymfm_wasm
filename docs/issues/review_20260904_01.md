## 所見

### P2: `playground.js` に起動・状態・UI 配線が集中している

`docs/playground/playground.js` は 1,159 行あり、次の責務を同じモジュールで持つ。

- DOM 要素の取得と hidden file input の生成。
- URL query の解釈、synth の生成、実行 runtime の初期化。
- VGM / Cassette の import と preset の更新。
- UI event handler の登録、初期表示、起動シーケンス。

とくに `playground.js:75` から `playground.js:260` の初期化用グローバルと、
`playground.js:628` 以降の event wiring が離れているため、変更時に状態の所有者や
初期化順を追いにくい。

### 対応方針

段階的に以下の単位へ分ける。

- `collectElements()` と `createImportInputs()` に DOM 構築を寄せる。
- `wireRuntime()` に synth / runtime / player の接続を寄せる。
- `installEventHandlers()` に UI event listener を集約する。
- `bootFromQuery()` に URL 起動時の分岐を集約する。

分割後も module 内の状態をただ移動するのではなく、各関数の入出力を明示して、
依存関係を呼び出し側で読める形にする。

### P2: VGM import の選択ロジックが二重に書かれている

`docs/playground/playground.js:494` の `importVgmFile()` は、VGM に含まれる chip と
選択中 chip の組み合わせを複数の boolean で表している。

`source` の選択は `playground.js:526` 付近、利用する import 方法の表示文言は
`playground.js:533` 付近で別々に分岐している。どちらも同じ判断を表すため、chip を
追加・変更したときに片方だけ更新される危険がある。

### 対応方針

`resolveVgmImportStrategy(vgm, selectedChip, options)` を作り、次のような値を一度だけ
決める。

```js
{
  source,
  statusMessage,
}
```

`importVgmFile()` は file 読込、strategy の解決、実行、UI 表示だけを順番に行う。
条件名も `isYm2608Only` のような入力データの事実と、`useNativeYm2608` のような
実行方針を混在させず、strategy 内に閉じ込める。

### P2: Cassette import が解析・検証・登録・描画を一度に行う

`docs/playground/playground.js:748` の `loadCassetteSource()` は、Cassette 読込後に
timbre / example を解析し、競合を検証し、preset と runtime を更新し、example select
を直接操作し、最終的な status text まで組み立てている。

この関数では `playgroundPresets`、`runtime.presets`、`cassetteExamples`、DOM の
`exampleSelect` が連続して更新される。部分的な仕様変更で更新漏れが起きやすく、
どこまでが pure な変換かも読み取りにくい。

### 対応方針

次の順序で小さな関数にする。

1. `parseCassetteAssets(source)` で timbre と example を抽出する。
2. `validateCassetteConflicts(assets, presets)` で追加可否を判定する。
3. `registerCassetteAssets(assets, stores)` でデータ状態だけを更新する。
4. `appendCassetteExamplesToUi(examples, exampleSelect)` で UI に反映する。

各段階の失敗時に state を変更しない契約にすると、import 失敗時の挙動も理解しやすい。

### P3: operator tab の synth 反映経路が散在している

`docs/playground/playground_operator_tab.js:425` の `applyChannelStateToSynth()` は
channel 全体を synth へ反映する。一方で Channel 3 special mode の周波数更新は
`playground_operator_tab.js:602` 以降の controls 内で直接行われ、pan 更新も
`playground_operator_tab.js:891` と `playground_operator_tab.js:907` で別々に
`synth.setPan()` を呼んでいる。

channel 3 special mode の対象 channel を表す `2` も複数箇所に現れる。状態を変更した
あとに何を synth へ反映すべきかを追うには、複数の handler を横断する必要がある。

### 対応方針

- `const SPECIAL_MODE_CHANNEL = 2` を導入する。
- `applyPanToSynth(channel)` に pan 反映を集約する。
- `applyChannel3SpecialOperator(operator)` に special mode 用周波数の反映を集約する。
- 通常 channel と special mode のどちらも、state 更新後は `apply...` 関数を経由する
  ルールに揃える。

これにより、control の event handler は「state を更新して反映関数を呼ぶ」だけになり、
UI ごとの違いが見えやすくなる。

### P3: bottom tab の定義が三箇所に重複している

`docs/playground/playground_ui.js:46` の `setBottomTab()`、
`playground_ui.js:80` の `moveBottomTabFocus()`、
`playground_ui.js:99` の `installBottomTabHandlers()` は、同じ tab と panel の対応を
それぞれ持っている。

tab を追加・改名したとき、表示切替、キーボード移動、click handler のいずれかだけが
古いままになる可能性がある。

### 対応方針

一つの tab 定義を共有する。

```js
const bottomTabs = [
  { tab: elements.operatorTab, panel: elements.operatorPanel },
  { tab: elements.mixerTab, panel: elements.mixerPanel },
  { tab: elements.effectTab, panel: elements.effectPanel },
];
```

`setBottomTab()`、focus 移動、event handler 登録はいずれもこの配列を利用する。
tab の順序と対応関係が一箇所で読めるため、UI 拡張の変更範囲も小さくなる。
