# VGM 再生の自動テスト方針

## 目的と現状

VGM の命令解釈、時刻、チップへの配送を自動テストで検証し、仕様への対応と回帰防止を進める。
音源技術を読み、調べ、学び、再構築できるようにするため、最小の VGM 入力と期待する命令列を
実行可能な資料として残す。

Parser → Mock Chip に加え、VGM Player に Mock SoundEngine を渡すテストを追加した。
通常命令と wait 中のストリームには同じ targets を渡し、本番の配送処理を通して検証する。
YM2612 DAC の主要仕様を修正し、シークのテストと CI 設定も追加した。
詳細な完了範囲と残作業は [追加テスト一覧](vgm_autotest_02.md) を参照する。

## テストする構成

```text
VGM Analyzer
  └─ VGM Player
       ├─ Parser：VGM 命令の解釈、wait とストリームの処理
       └─ SoundEngine：書き込みの受付、音声の生成
            ├─ 本番：既存の音源コアを使用
            └─ テスト：Mock が命令と時刻を記録
```

同じ Player と Parser に同じ VGM バイト列を渡し、SoundEngine を差し替える。
テストでは Analyzer の画面、WASM、AudioContext を起動せず、音声バッファの処理を明示的に進める。
警告欄の表示や曲の切り替えなど、画面固有の挙動は別の UI テストで確認する。

| 層 | 検証する内容 |
| --- | --- |
| Parser → Mock Chip（追加済み） | 命令の解釈、配送先、値、順序、VGM 時刻 |
| Player → Parser → Mock SoundEngine（追加済み） | 本番の配送経路、wait、出力バッファの分割、リセット、pause/resume |
| 実 SoundEngine のテスト | 音声生成、PCM/ADPCM メモリ、ミキサーなど |
| UI・実曲確認 | 警告の表示、操作、実曲の再現性と聴感 |

## SoundEngine の差し替え

現在の `VgmPlayer` は `constructor(engine)` でエンジンを受け取る。
この入口を使い、本番と同じインターフェースを持つ Mock を渡す。
既存の Parser テストは、生成済みの Mock チップを `playStep(targets)` と
`consumeWait(targets, ...)` に直接渡しており、Player は経由していない。

生成関数を共通化する場合は、次のような構成を目指す（概念例。新しい API の実装済み例ではない）。

```js
const engine = await createSoundEngine(chipName, options);
const player = new VgmPlayer(engine);
```

- 本番では実エンジン、テストでは Mock を返す生成関数を渡す。
- WASM 初期化に合わせて生成は非同期にできるようにする。命令ごとに生成しない。
- 複数チップは種類とインスタンス番号で登録し、再生中は同期的に対象を取得する。
- `resolveChip(type, index)` / `getVgmTarget(type, index)` の登録先解決を共有する。
- チップごとのポートやメモリ操作の変換を、テスト側で別実装しない。
- Parser や Player に本番・Mock を判定する分岐を追加しない。
- 未登録の第2インスタンスを第1インスタンスへ代替配送しない。

同一チップ2基を表現できる設計を維持する。2基構成の実音源による再生検証は今回の対象外とする。
DAC ストリームのインスタンス配送は、通常書き込みとは別に未完了項目として扱う。

## Mock が記録するもの

Parser の Mock は次の共通ログ形式を使い、全チップの呼び出しを一つの配列に記録する。

```js
{
  sample: 100,
  chip: 'ym2612',
  instance: 0,
  method: 'register',
  args: [0, 0x2a, 0x80] // port, register, value
}
```

`sample` は VGM の 44,100 Hz 時間単位。上の値は記録形式の例であり、特定命令の期待時刻ではない。
メモリロードは送り先、オフセット、サイズ、データ内容も記録する。
配列全体を比較し、余計な書き込み、欠落、別チップへの誤配送、同時刻の順序の違いを検出する。

Mock SoundEngine は Player が必要とする生成・リセットなどの操作を提供し、
音声生成要求には指定長の無音バッファを返す。実時間のタイマーには依存しない。
出力サンプル数と VGM 時刻は区別し、最初は出力 44,100 Hz で期待時刻を確認する。
その後、48,000 Hz などでも端数の繰り越しやバッファ分割で命令時刻がずれないことを検証する。
実際の音源呼び出し位置で記録し、Parser のイベント列を配送結果の代わりに使わない。

追加した Mock SoundEngine では `sample` の代わりに `frame` を記録する。これはエンジンが
生成済みの出力フレーム数であり、48 kHz では VGM 時刻と異なる。期待値はテスト側で明示する。
現在の Mock は YM2612・AY・YM2413・Y8950・PWM・PSG の書き込みを受け付ける。
全チップやメモリロードの Player 経由テストは今後拡充する。

## DAC ストリームの残課題をテストから実装する

[DAC 対応状況と残課題](dac_01.md) の未完了項目ごとに、最小の VGM と期待ログを用意する。
仕様に基づいて期待値を明示し、修正前に失敗することを確認してから実装する。
現在の出力をそのまま正解として保存し、既知の不具合を固定することは避ける。

| 対象 | 確認する結果 |
| --- | --- |
| `0x91` のステップ幅・`stepBase` | 指定した位置の値が指定した順序で届く |
| `0x93` の各長さモード | 命令数・時間・末尾・長さ維持に応じた書き込み回数と停止位置 |
| 開始位置 `0xFFFFFFFF` | 仕様が定める位置の扱いと再開時の値列 |
| 逆再生・ループ | 先頭・末尾での値の順序、終了または繰り返し |
| `0x95` のブロック選択 | 指定バンク内のブロックからデータが届く |
| `0x95` のループフラグ | 指定どおり繰り返し、または停止する |
| 初回書き込み・周波数変更 | 仕様と照合した時刻に書き込む |
| 停止・全停止・予約 ID | 停止対象以外の演奏が続き、不正な再有効化が起きない |
| 未対応の送り先 | 警告し、そのストリームだけ省略して他の演奏を続ける |
| 複数ストリーム | それぞれの送り先・周期を保持し、相互に状態を壊さない |

同じ値列を通常のレジスタ書き込みとストリーム命令で表現し、Mock の配送ログが一致するケースも作る。
まずそれぞれを明示した期待値と比較し、その上で両経路の一致を確認する。
既存 PWM ストリームのテストを回帰確認に含める。

## 実装と検証の順序

1. Player が必要とする SoundEngine のインターフェースを整理し、Mock を渡せるようにする。
2. Player 経由で通常書き込み、wait、終端の期待ログを検証する。
3. バッファを小さく分割しても結果が一致すること、リセット後に同じログを再現することを確認する。
4. DAC の未完了項目ごとに仕様ベースの失敗するテストを追加し、実装を修正する。
5. 通常再生とシーク後の同じ区間を比較する。シークのための再実行ログは区別して記録する。
6. 異なる出力サンプルレート、複数チップ、既存 PWM と警告処理の回帰を確認する。
7. `web/` と配信用 `docs/js/` を同期し、同じケースを適用する。
8. 自動テストを CI で継続実行できる入口を整備する。

テストには仕様上の根拠、入力の意図、期待する値列・時刻を残す。
仕様や参照実装で解釈を確認する必要がある項目は、確認してから期待値を確定する。
不具合を発見したら、再現できる最小ケースを追加してから修正する。

このテストで命令解釈と配送を検証できるが、音質や実曲の完全な再現性は保証しない。
合成データによる自動テストと、実音源・実曲で確認した結果は分けて記録する。


生成関数の共通化は行わず、既存の `new VgmPlayer(engine)` に Mock を渡している。
