# 外部クロックを受け取る時間制御の設計メモ

状態：相談内容をまとめた未実装・未確定の案。既存 API の変更・廃止を決めるものではない。

関連：[複数音源と useSoundChip](multisoundchip_01.md)／[YM2612 DAC の PCM API](../ym2612-dac-pcm.md)

## 背景

DAC の API を整理する中で、音源の操作と演奏の時間制御の境界が問題になった。

Playground は `sleep()`・`beat()`・`sleepSamples()`・`liveLoop()` などを提供し、演奏位置と音声側の時刻をつないでいる。一方、音源を Playground の外から利用する場合にも、PCM やレジスター操作の予約が必要になる。

「時間の調整は Playground の責務」とだけ整理すると、他の環境で同じ仕組みを使いにくくなる可能性がある。MIDI クロックのように外部から共通の拍・時刻を受け取り、各 Object が自分の処理へ反映する構造を検討したい。

ここでの「MIDI のように」は外部の時間源に追従する発想を指す。MIDI プロトコルの実装や特定の通知間隔を採用すると決めたわけではない。

## 検討する方向

時間制御を独立した部品にし、Playground もその利用者にする。

| 対象 | 担当する役割 |
|---|---|
| 外部の時間源 | 拍・時刻・開始／停止などを通知する |
| 共通の演奏クロック／トランスポート | 演奏位置、テンポ、開始・停止を管理し、外部の時間源との対応を保つ |
| 各音源 Object とバックエンド | 共通時刻で予約を受け取り、自分の音声フレームへ変換して実行する |
| Playground | `beat()`・`sleep()`・`liveLoop()` などを共通の時間制御につなぐ |

各音源が担当する「調整」は、共通時刻を自分の処理へ対応付けること。各 Object が独自の時計やタイマーで進行し、別々にテンポを決める構造は避けたい。

共通クロックと開始・停止・予約キャンセルを管理する演奏トランスポートを、同じ Object にするか別の Object にするかは未決定。

## 通知の到着時刻と発音時刻を分ける

単に「通知が届いたら鳴らす」方式では、通信や JavaScript の処理の遅れが発音時刻に影響する。

音源が受け取る情報は、可能なら「共通時計のこの時刻に実行する」という予約にする。実際のレジスター更新や PCM の供給は、音声を生成するバックエンドが担当する。

- Web：音声側の時計・フレームへ対応付け、AudioWorklet 内で実行する。
- Node.js のオフライン生成：生成済みフレーム数で時間を進め、該当する位置で実行する。実時間の待機は不要。
- 外部クロック：拍の通知からテンポや位相を追跡し、演奏位置へ対応付ける仕組みを検討する。

外部の拍の通知と、音声フレーム単位の実行精度は別の問題。通知間の進行、揺れの吸収、遅れたイベントの扱いを決める必要がある。

## API のイメージ

以下は責務の配置を示す案であり、現在動くコードではない。`clock` オプションやその型は未実装。

```js
// 提案：ホスト環境が用意した共通クロックを音源へ渡す。
const synth = new YM2612Synth({
  transport,
  clock: performanceClock,
});
```

クロックを Synth へ注入するか、レジスター通信を担う transport／予約処理を担うアダプターへ渡すかは、既存実装を調査して決める。目的はクロック引数を増やすことではなく、Playground の外でも共通の演奏位置を使えるようにすること。

DAC のデータ登録と再生は引き続き分ける。

```js
// 現在の API。将来の時刻体系でも、この用途が読める形を維持したい。
await synth.dac.setSample('voice', pcmBytes, { sampleRate: 11025 });
await synth.dac.playFromSample('voice');
```

PCM の登録・保持は音源側の役割であり、クロック側には持たせない。ロード完了を待ってから演奏を開始する流れも維持する。

## 時刻の意味を明確にする

少なくとも次の値は区別する。

| 値 | 意味 |
|---|---|
| 拍・tick | 音楽上の進行位置。テンポとの対応が必要 |
| 演奏開始からの秒 | 曲・演奏のタイムライン上の位置 |
| 音声時計の絶対秒 | Web の AudioContext など、バックエンド固有の時計 |
| 出力フレーム番号 | 実際に音を生成する位置。出力サンプルレートに依存 |
| PCM のサンプル位置 | 登録した音声データ内の位置。その PCM のサンプルレートに依存 |

既存の `scheduleWritesSamples()` の時刻は固定の「44100単位＝1秒」であり、PCM 音源専用の API ではない。今回の相談では名前を維持することにした。共通クロックの導入に合わせて、既存の単位を暗黙に変更しない。

現在の DAC API の `when` は、Web では音声時計の絶対秒、Node.js の DirectTransport では生成フレーム数から求める秒を指す。共通の演奏タイムラインへ移すなら、既存の意味を保つ方法や明示的な変換方法が必要になる。

## 未決定の点

- 共通クロックの所有者と、複数の音声バックエンドへの接続方法。
- 外部の通知にタイムスタンプがある場合／ない場合の扱い。
- テンポ変更時、予約済みの拍ベースのイベントを再計算する範囲。
- 外部クロックの揺れ・途切れ・再接続への追従方法。
- 遅れたイベントを即実行するか、飛ばすか、エラーにするか。
- Stop／Pause／Resume／Seek／ループ折り返し時の時計と予約の扱い。
- ライブ編集時に保持する演奏位置と、古い実行の予約を無効化する方法。
- 複数の `liveLoop` が共有する時刻と、それぞれの演奏位置の管理。
- バックエンド間のサンプルレート・時計の原点の違いを吸収する場所。
- 共通化するインターフェースと、音源固有の操作を残す範囲。

## 次に進める場合の順序

1. Playground の時間管理、予約処理、Main／Worker／AudioWorklet の時刻変換を調査する。
2. 各 API の時刻単位・原点・所有者を一覧にし、外へ取り出せる責務を特定する。
3. Web と Node.js で、同じ演奏イベントを共通タイムラインから実行する小さな試作を作る。
4. Stop、再実行、複数音源、遅延したイベントを検証する。
5. 既存 API の意味を保つアダプターを検討し、Playground の待機・ループ機能を接続する。
6. その上で、外部クロックへの追従やテンポ変更を検討する。

このメモでは設計の方向と検討点を整理する。ランタイムや公開 API の変更は行わない。
