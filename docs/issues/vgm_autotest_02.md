# VGM 自動テストの不足項目

## 位置づけ

[自動テスト方針](vgm_autotest_01.md) に対し、今後追加するケースを整理する。
この文書はテスト追加の作業一覧であり、以下の仕様対応や検証が完了したことを意味しない。

対象は主に `vgm-parser-mock.test.mjs` と `vgm-player-mock.test.mjs`。
既存の音源別テストに部分的な検証がある場合も、Player → Mock の経路で不足しているものを含む。
YM2612 DAC の仕様修正は [dac_01.md](dac_01.md) と対応づけて進める。

## 現在の到達点と限界

- Parser の Mock は通常書き込み20形式、wait、終端、MSX の配送、Y8950 のメモリロード、
  リセット、PWM ストリーム、不完全な通常書き込みを検証している。
- Player の Mock は YM2612 の両ポート、AY・YM2413・Y8950 の交互書き込み、wait、終端、
  リセット、pause/resume、PWM の直接書き込みとの一致、48 kHz の端数処理、未対応 DAC の継続を検証している。
- Player の Mock は従来の `writeYm2612` などを受け取る。`getVgmTarget` を使う実際の
  複数チップ登録経路や、メモリロードはまだこのテストでは検証していない。
- 出力バッファのサイズ変更は確認済み。ただし Player は一つの wait をまとめて描画するため、
  バッファサイズ変更だけでストリームの wait 分割境界を網羅したことにはならない。
- Mock の音声は無音。命令ログが正しくても、音声バッファの欠落・重複をそれだけでは検出できない。
- Parser の `sample` は VGM 時刻、Player Mock の `frame` は生成済みの出力フレーム数。
  異なるサンプルレートでは同じ単位として比較しない。

## 優先度1：YM2612 DAC の仕様ベースのテスト

以下は Parser と Player の両方で検証する。期待する値列と時刻を仕様から決め、
修正前に失敗することを確認してから実装を直す。既知の誤動作を期待値にしない。

| 状態 | ケース | 確認する結果 |
| --- | --- | --- |
| [ ] | `0x91` の `stepBase` とステップ幅 | 識別可能な値を並べたバンクから、指定位置の値だけが順に届く |
| [ ] | `0x93` の各長さモード | 命令数・ミリ秒・末尾まで・長さ維持を個別に確認し、回数と停止位置が合う |
| [ ] | 開始位置 `0xFFFFFFFF` | 再設定・再開時も仕様に従う位置から値が届く |
| [ ] | 逆再生 | 先頭・末尾・1要素の区間で順序と停止位置が合う |
| [ ] | `0x95` のバンク内ブロック番号 | 異なるバンクに同じ番号のブロックを置き、指定バンクの値だけが届く |
| [ ] | `0x95` のループフラグ | ループ指定の有無で、繰り返しと停止が正しく切り替わる |
| [ ] | 初回書き込み | 開始命令と最初の wait の境界で、仕様に従う時刻に1回だけ届く |
| [ ] | 周波数変更 | 演奏途中の変更後も周期と位相の扱いが仕様に合う |
| [ ] | 停止・全停止・再開 | 停止後に余計な値が届かず、他ストリームは必要に応じて継続する |
| [ ] | 予約 ID `0xFF` | 全停止以外の命令で通常のストリームとして作られない |
| [ ] | 複数ストリーム | 異なる周期・送り先で状態が混ざらず、同時刻の処理順が確認できる |
| [ ] | 直接書き込みとの比較 | 同じ演奏を通常命令とストリームで表し、双方が明示した期待ログに一致する |

空バンク、範囲外の開始位置、0件の長さ、0 Hz、ステップ幅0なども追加する。
これらの期待結果は、仕様に定義があるかを先に確認する。未定義の場合は、
アプリとして採用する警告・無効化などの方針を記載してからテストする。

## 優先度2：Player の配送経路とメモリ

- [ ] Parser で検証済みの通常書き込み20形式を、Player 経由でも確認する。
      OPM・OPN・OPNA・OPNB・OPL・OPL3・OPL4・RF5C164 などのアダプターを対象にする。
- [ ] PSG の値を Player 経由で確認する。Mock にメソッドが存在するだけでは検証済みとしない。
- [ ] `getVgmTarget(type, index)` を提供する Mock で、複数チップ登録経路を確認する。
      従来メソッドへの誤った代替呼び出しも検出する。
- [ ] Y8950・YMF278B・OPNA・OPNB・RF5C164 のメモリ操作を、対応する Player 経路で確認する。
      データ、送り先、オフセット、サイズ、ロードとレジスタ書き込みの順序を比較する。
- [ ] 曲の切り替え時に必要なメモリクリアが呼ばれ、前の曲のデータが残らないことを確認する。
- [ ] リセット時に必要なメモリが再ロードされ、同じ配送ログが再現することを確認する。
- [ ] 未登録のインスタンスを第1チップへ配送しないことを Mock で確認する。
- [ ] DAC のインスタンス対応を実装する際、通常命令と wait 中の書き込みが同じ登録先へ届くことを確認する。

同一チップ2基の実音源による再生検証は今回の対象外。Mock による登録先の区別は、
実音源での2基構成の動作保証とは分けて記録する。

## 優先度3：時刻・再生操作・シーク

- [ ] ストリーム周期の直前・一致・直後で `consumeWait()` を分割し、書き込みの欠落・重複がないことを確認する。
- [ ] 非整数周期のストリームを長めに流し、累積誤差と最終的な書き込み数を確認する。
- [ ] 44,100 Hz 未満の出力も使い、出力0フレームになる短い wait の後も端数が保持されることを確認する。
- [ ] 出力フレームが同じ位置に丸められる複数の命令について、配送順が保たれることを確認する。
- [ ] DAC が動作中の pause/resume、stop/play、reset を確認する。通常書き込みだけのケースと区別する。
- [ ] ループ位置あり・なしの両方で、DAC の値列・周期・バンク状態を確認する。
      通常の Player ループには既存テストがあるため、ストリーム固有の状態を追加対象にする。
- [ ] Analyzer の実際のシーク経路をテストへ接続する。Player にシーク API があると仮定して別実装しない。
- [ ] ストリームの途中、開始・停止境界、メモリロード後へシークし、通常再生の同区間と比較する。
      シークのために先頭から再実行したログは、到達後のログと分ける。

## 優先度4：不正入力・警告・出力の保全

- [ ] DAC 命令とデータブロックを各バイト位置で切断し、不完全な書き込みやメモリロードが届かないことを確認する。
- [ ] 不正なブロックサイズ・オフセットなどで、無限ループや無制限の処理にならないことを確認する。
- [ ] 未対応ストリームと対応済みストリームを同時に動かし、対応済みの演奏が維持されることを確認する。
      未対応ストリーム単独の警告・再有効化防止は既存テストがある。
- [ ] 曲の切り替え後に前の曲のストリーム状態が残らないことを Player 経由で確認する。
- [ ] 無音 Mock に加え、連番など識別可能な音声を返す Mock で、バッファ境界の欠落・重複・左右の取り違えを確認する。
      既存 `vgmplayer.test.mjs` のキュー・pause・loop テストを活用し、未検証の条件を追加する。
- [ ] UI の警告表示・消去を実際の Player の警告通知に接続して確認する。
      警告欄単体のテストと、Player から画面までの接続テストを区別する。

## テストを継続するための整備

- [ ] WASM 不要の Parser / Player Mock テストをまとめて実行する入口を用意する。
- [ ] CI で実行し、失敗時に期待ログと実ログの差分が分かるようにする。
- [ ] 新しいケースも `web/` と `docs/js/` の両方に適用する。
- [ ] 各ケースに、仕様の根拠、入力の意図、期待値、関連する不具合を記録する。
- [ ] 必要に応じて固定シードの組み合わせテストを加える。失敗例は最小化して通常の回帰ケースとして残す。

テスト件数だけを完了基準にせず、各項目について「どの入力で、何を検証したか」を残す。
実チップの音質・実曲の再現性は別の検証として扱う。
