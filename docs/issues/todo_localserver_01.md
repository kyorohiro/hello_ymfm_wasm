# Playground：ローカルサーバー方式への統一案

作成：2026-10-13

状態：検討メモ。ローカルサーバー方式への移行は未実装。以下の構成・段階は提案であり、採用を確定したものではない。

## 目的

Playground の native 機能をローカルサーバーから利用できるようにする。
Tauri の WebView と通常のブラウザで、同じ画面と同じ API を利用する構成を検討する。

Tauri command 方式とローカルサーバー方式を並行して実装すると、機能・認証・エラー処理・テストの二重管理になりやすい。
移行する場合は、native 機能へのアクセスをローカルサーバーの API に寄せる。
Tauri はサーバーの起動・終了、ウィンドウ、トレイなどのアプリ管理を担当する。

背景には、code-server のようにブラウザから開発環境を使う構成と、今後の音楽・ロボット対戦・ドローンシミュレーションなどへの Playground の展開がある。
今回の検討は、code-server 自体の組み込みを前提にはしない。

## 現在の構成

- ブラウザ版は、編集・Virtual Files・ローカル Git 操作・音楽実行をブラウザ側で行う。
- Tauri 版は、native 音声、Git の HTTPS 通信、OS の資格情報ストアなどを Tauri command 経由で利用する。
- Git のローカル操作は JavaScript の実装を共有する。Git の履歴と index は Virtual Files 内の `/.git` にある。
- Tauri 版のプロジェクト自動保存は IndexedDB を利用している。
- PAT の登録・選択は native ダイアログを利用し、秘密の値を JavaScript に返さない。
- MCP 用のローカル HTTP サーバーはすでに存在する。

現在の MCP の主な流れ：

```text
AI / MCP クライアント
  → ローカル HTTP サーバー
  → Tauri の WebView
  → Playground の操作・実行
```

MCP の HTTP サーバーがあることと、通常のブラウザから native 機能を利用できることは別。
現在の MCP は、実行中の WebView に処理を渡す構成であり、画面なしで独立動作する Playground サーバーではない。

## 提案する構成

```text
Tauri WebView ─┐
              ├─ HTTP / WebSocket ─ Rust サービス
通常のブラウザ ─┘                      ├─ Git HTTPS / 資格情報
                                     ├─ プロジェクト保存（検討）
                                     └─ native 音声（必要な場合）

Tauri：サービスの起動・終了、ウィンドウ・トレイなどの管理
Rust サーバー：Playground の静的ファイル配信、API、接続管理
画面：編集・表示・Virtual Files・JavaScript 実行
```

業務処理を WebviewWindow / AppHandle やダイアログから分離する。
通信の入口、実処理、画面操作を分け、WebView とブラウザの違いによって業務処理を複製しない。

HTTP と WebSocket の分担は未決定。
設定・Git の要求と応答、状態通知、音声の命令列では通信の性質が異なるため、一律に JSON の単発要求へ置き換えない。

MCP は既存の通信・認証実装を参考にできる。
ただし、MCP の入口と画面用 API は役割が異なるため、同一エンドポイントに統合すること自体を目的にしない。

## ローカルサーバー方式の欠点と検討事項

| 項目 | 増える負担・影響 | 検討する対応 |
|---|---|---|
| 認証・権限 | localhost でも、他のアプリや Web ページからの要求を考慮する必要がある。Tauri IPC のアクセス制御を HTTP API が自動で引き継ぐわけではない | 接続用の認証、Origin / Host の検証、要求の入力検証。CORS だけを認証代わりにしない |
| 起動・終了 | サーバー起動待ち、ポート競合、複数アプリ起動、終了時の接続切断が発生する | 接続先の通知、起動失敗表示、再接続、終了時の保存・音声停止を設計する |
| 複数タブ | 同じ API に複数画面が接続できる。編集・演奏・MCP の対象が曖昧になる | プロジェクト ID、接続セッション、操作対象、同時編集・実行の方針を決める |
| 資格情報の UI | 外部ブラウザから要求した native ダイアログが別ウィンドウに現れると、フォーカスや操作が分かりにくい | PAT 登録はアプリの設定画面で行い、ブラウザには名前・ID だけを返す方式などを検討する |
| 保存 | IndexedDB はオリジン単位。ポートが変わると以前の保存領域を直接利用できなくなる | 固定オリジン、既存保存の移行、Rust 側でのプロジェクト保存を検討する |
| native 音声 | 細かい音声命令を単発の通信で送ると、遅れ・詰まり・再接続後の残存命令を扱う必要がある | まとめ送り、時刻指定、キュー上限、実行世代、停止・切断時の破棄。実測して判断する |
| ブラウザ対応 | 外部ブラウザも対象にすると、ブラウザごとの動作・権限・音声開始の制約を確認する範囲が増える | 対応範囲を決め、主要な操作をブラウザでも検証する |
| 画面なしの動作 | サーバーを起動するだけでは、現在 WebView が持つ Virtual Files や liveLoop の実行状態は存在しない | ブラウザを実行主体にするか、別の JavaScript 実行環境を用意するかを区別する |

Git や設定操作については、通信速度より接続・認証・状態管理の負担が中心と考えられる。
音声については、遅延や安定性を推測だけで決めず、現在の native 経路と比較して測定する。

PAT は引き続き Rust / OS の資格情報ストアで管理する。
通信方式を変えても、PAT の値を画面に返したり、Virtual Files・Cassette に保存したりしない。

## 先に決める事項

1. **複数タブを許すか**
   - 一つの画面だけを操作主体にするか。
   - 複数画面で同じプロジェクトを共有するか、画面ごとに独立させるか。
   - MCP が操作する接続・プロジェクトをどう選ぶか。
2. **プロジェクトを誰が保持するか**
   - ブラウザの Virtual Files が正となるか、Rust が正となるか。
   - 保存・復元、競合、接続切断後の未保存編集をどう扱うか。
   - 既存の IndexedDB データをどう移行するか。
3. **音をどこで鳴らすか**
   - ブラウザ音声なら、画面を開いた端末で鳴る。
   - native 音声なら、サーバーを動かしている PC で鳴る。
   - 実行主体と音声出力先を区別して設計する。
4. **公開範囲をどこまでにするか**
   - 最初は同じ PC の localhost 接続に限定する案。
   - LAN の別端末からの接続や HTTPS 対応は別段階として検討する。
   - itch.io のブラウザ完結版は、サーバーなしで利用できる構成を維持する案。

## 移行する場合の段階案

- [ ] 上記の状態・接続・音声の方針を決める。
- [ ] 現在の command ごとに、実処理と Tauri / ダイアログ依存を棚卸しする。
- [ ] Rust の実処理を分離し、通信 API の要求・応答・エラー・キャンセルを定義する。
- [ ] 静的ファイル配信と認証付き localhost API を試作する。
- [ ] WebView と通常のブラウザで、同じ API を呼ぶことを確認する。
- [ ] Git 通信・資格情報の UI・保存を移行し、既存データの引き継ぎを確認する。
- [ ] native 音声が必要な場合は、通信方式を検証して遅延・停止・再接続を測定する。
- [ ] MCP の操作対象と接続管理を新しい構成に合わせる。
- [ ] 移行済みの機能の旧 command 経路を削除し、恒久的な二重管理を残さない。

移行中の一時的な共存と、二方式を永久に保守する構成は区別する。
Tauri のウィンドウ管理など、Tauri 自体の管理に必要な処理は残してよい。
