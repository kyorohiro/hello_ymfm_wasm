# Run切替とliveLoopのサンプル時計

2026-10-16

## 確認した現象

`www/my-project.cassette/index.js` と `03 - Jungle (Exploration).js` を
Runボタンで切り替えると、Jungleへ戻った直後に再生位置が飛び、書き込みが集中する。
独立したChromiumの実際のRun操作で、100件以上のFM発音・停止・設定が
約5.3msに集中することを確認した。ノイズのPCM波形そのものは比較していない。

## 原因と修正

`sleepSamples()` は、セッション共通の原点とループごとの累積位置を使う。
Runで別のループへ切り替えても原点は残るが、新しいループの累積位置が0だったため、
過去の期限を追いかけて待機なしで進んでいた。MainとWorkerの両方に存在した。

新しく作るループには、現在の共通タイムライン位置を与える。
1回のcommitで位置を一度だけ取得し、複数チャンネルを同じ位置から始める。
継続中の同名ループの位置・待機・次周での関数差替えは維持する。
共通の原点も維持し、既存の音声予約の座標を動かさない。
Workerは従来の先読み時間を含む時計を維持する。

Workerの削除→同名再追加も修正した。旧ループが非同期cleanup中に残っていると、
名前だけの実行中判定により新ループを開始できないことがあった。
実行コンテキストで停止と再登録を識別し、旧ループのfinallyが新ループを削除しないようにする。

`beginSampleSchedule()` は共通の44,100Hzタイムライン上の累積位置を返す。
後から作ったループでは最初の値も0とは限らない。
この値をそのまま `scheduleWritesSamples(startSamples, entries)` に渡せる。
素材の先頭から何秒再生したかを表す値ではない。

## Runの仕様

| 操作 | 動作 |
| --- | --- |
| 同じ名前のliveLoopを再Run | 現在の関数呼び出しを終え、次周の先頭から新しい関数を実行する |
| 次のコードに同じ名前がない | そのループの待機をキャンセルして終了する |
| 新しい名前のliveLoopをRun | 関数の先頭から、今回の開始位置を基準に実行する |
| StopしてからRun | ループ・音声を停止し、サンプル時計も初期化して始める |

ファイル名ではなくliveLoop名で判定する。
Jungleの9ループは各2,651,880サンプル、約60.13秒が1周である。
同名で再Runした際は、最大でその周回の残り時間だけ旧コードが続く。
新しい関数の途中へジャンプする仕組みではない。

## 残る制約と別のノイズ要因

- 新コードのトップレベルは、旧ループが動いている間に評価される。
  定義のcommitは評価成功後であり、トップレベルの音声操作を遅延する仕組みはない。
  今回のindex.jsはファイル読込より前に `fm.reset()` を呼ぶため、
  リセット後に旧VGMループがレジスターを書き戻す時間帯があり得る。
- Runは全音声を停止する操作ではない。rawレジスターによる発音や
  予約済みイベントを、ループ削除だけで一律に消去することはない。
- 今回のRFループはキャンセル時のcatchで `rf.dispose()` を呼ぶ。
  音が鳴っている途中の接続解除は波形の段差になり得る。
- Jungleはサンプル単位のJS待機後に即時書き込みするコードである。
  2〜3サンプルの待機まで音声サンプル精度で実行する保証はなく、
  UI負荷による通常の起床遅延は今回の修正後も別の制約として残る。
- 新しいMainループが即時書き込みの時計へ参加する際、追加の先読み時間は付けない。
  その位置で音声予約も開始する場合、先頭の予約には十分な先読みがないことがある。

これらを隠す自動スムージングや、全Runを強制的に最初から再生する変更は行わない。
利用者のCassetteコードも変更しない。

## 追加対応：長期間失敗していたDAC変換テスト

同日、利用者の依頼を受けて修正。
9月2日作成のfixtureが、9月14日のDACストリーム処理修正
（`709cf91`）に追従していなかった。

- `0x93` のlength modeが0だった。0は前回の長さを再利用する指定であり、
  初回の長さ3を設定するテストには1（コマンド数指定）が必要。
  fixtureを1に直し、DACストリーム対応版のVGM 1.71ヘッダーも明示した。
  [VGM仕様](https://raw.githubusercontent.com/vgmrips/vgmplay-legacy/master/VGMPlay/vgmspec171.txt)
- 既存のPlayground／parserモデルは開始位置で最初のバイトを出力するため、
  44,100Hzストリームの位置は0・1・2サンプル。古い1・2・3の期待値を修正した。
  仕様本文は初回出力の位相を明文化していないため、仕様で0を要求しているとは扱わない。
  libvgmの次の更新境界で初回出力する実装へ合わせる変更も、今回行わない。
- テスト名の「ReadableではDACを省略」も古く、実際にはpacked bankとして保存される。
  テスト名を修正し、packed bank全15バイトの時刻・値を厳密に確認する。
- mode 0で未設定の長さ3を指定しても発音しない回帰テストを追加。
  web／docsのparserとplayerの両方で確認し、既存の長さ再利用テストも維持する。

追加した `dac_stream_export.test.mjs` では、変換コードを実行した結果を
実際のWorklet DACスケジューラーとYM2612 WASMへ渡して比較する。
Write／Schedule／High × raw／Base64／外部ファイル × 44,100／48,000Hz ×
開始位置0／4,410サンプルの36経路で、元VGM PlayerとDAC書込時刻・順序、左右PCMが完全一致した。
同時刻のDAC直接書き込みも含め、単にデータ読み込み関数が出力されるだけの確認にしない。

Playground全体とDAC関連514テストがすべて成功（失敗・スキップ0）。
この不整合を直すための再生エンジン変更は不要だった。
